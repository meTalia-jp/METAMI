# 03_AI開発ルール・Git運用

## 目的
この文書はCodex、Continue、その他のAI開発エージェントに共通して適用する。
AIを過度に拘束するのではなく、必要な裁量を与えながら、
仕様逸脱と未検証の完了報告を防ぐことを目的とする。

## 人間側の前提
ユーザーはコードの詳細確認を前提としない。
最終判断は主に以下で行う。

- 実際にアプリが起動するか
- 指定した操作ができるか
- 画面表示が要件どおりか
- AIからの日本語説明が理解できるか

## AI開発エージェントの基本ルール
1. 作業開始前に`docs/`内の関連仕様を確認する。
2. 指定されたバージョンの完了条件を満たすことを最優先にする。
3. 実装方法、内部設計、関数分割、例外処理、テスト追加は合理的な範囲でAIが判断してよい。
4. 軽微な不足や矛盾は、既存仕様の目的に沿って判断して進めてよい。
5. 次に該当する場合だけ、作業前に質問または提案を行う。
   - アプリの目的や主要機能が変わる
   - 対応形式や保存方式が変わる
   - 大きな外部依存関係が必要になる
   - ユーザーファイルの変更・削除を伴う
   - 仕様同士が明確に矛盾し、合理的に解決できない
6. 指定バージョンのために必要な小規模修正は、関連ファイルも含めてまとめて実施してよい。
7. 既存コードが破損・空・明らかに不適切な場合は、目的を保ったまま作り直してよい。
8. 実装後は、実際に変更したファイルを再確認する。
9. 実行可能な環境では、構文確認または起動確認を行う。
10. 確認できていないことを「確認済み」「正常動作」と断定しない。

## 禁止ではなく事前確認とする事項
以下は一律禁止しない。ただし、必要性がある場合は理由を説明する。

- 新しい外部ライブラリの追加
- 既存ファイルの大幅な書き換え
- フォルダ構成の変更
- リファクタリング
- テストコードやログ機能の追加
- UIの細かな改善

## 完了報告
作業完了時は日本語で以下を報告する。

1. 実装・修正した内容
2. 変更したファイル
3. AIが実施した確認
4. ユーザーが行う動作確認
5. 未確認事項または残っている問題
6. 仕様外の改善提案がある場合は「提案」として分離

「完了」は、ファイルを変更しただけではなく、
指定バージョンの完了条件を満たす状態を意味する。

## エラー対応
ユーザーから以下を受け取ったら調査する。

- エラーメッセージ全文
- 直前に行った操作
- 可能なら画面または対象ファイル

AIは原因候補を並べるだけで終わらず、
可能な範囲で修正し、再確認方法を示す。

## Git運用
- 正常動作が確認できた状態を基準点としてコミットする
- AIの完了報告だけでは正式な完了コミットにしない
- ユーザーが動作確認した後にコミットする
- 1つのバージョンまたは意味のまとまった機能単位でコミットする
- 大きな変更前には正常動作版をコミットしておく
- 各Ver完了時に`docs/CHANGELOG.md`を更新する
- Codex版とContinue版を比較する場合は、同じ作業フォルダを同時編集せず、ブランチまたはworktreeを分ける

## 共通実装依頼テンプレート

```text
docsフォルダの仕様を確認し、VerX.Xを実装してください。

仕様を満たすための内部設計や小規模な関連修正は、合理的に判断して進めてください。
主要仕様の変更や大きな依存関係の追加が必要な場合だけ、実装前に確認してください。

実装後は、変更ファイルを再確認し、可能な範囲で構文確認・起動確認を行ってください。
確認できていない内容を「確認済み」と報告しないでください。

最後に日本語で、変更内容、変更ファイル、実施した確認、
私が行う動作確認、未確認事項を報告してください。
Gitコミットは行わないでください。
```

## エラー修正テンプレート

```text
以下の問題を修正してください。

直前の操作:
（ここに記載）

エラーまたは現象:
（全文を記載）

関連する仕様を確認し、原因を調査して修正してください。
必要な関連修正は合理的な範囲で行って構いません。
修正後は変更ファイルを再確認し、確認できた内容と未確認事項を日本語で報告してください。
```
